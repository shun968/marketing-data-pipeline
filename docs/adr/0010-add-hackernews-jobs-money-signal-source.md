# ADR-0010: Hacker Newsの求人・案件スレッドを金の流れシグナルの収集元として追加する

- ステータス: 採用
- 日付: 2026-08-11
- 関連: [ADR-0006](./0006-add-hackernews-demand-signal-source.md) / [ADR-0009](./0009-add-github-and-reddit-demand-signal-sources.md) / [requirements.md](../requirements.md) §3.1 / [design.md](../design.md) §4.3

## コンテキスト

既存5プラットフォーム（Bluesky / YouTube / Hacker News / GitHub / Reddit）はすべて需要シグナル（困りごと）または供給シグナル（既存ソリューション）を担う。この構成では**支払い意思が観測できない**という限界が実データで表面化した。

- 構造化抽出済みの全期間で `monetizable=true` は**5件**しかない。うち `pain_level=3` は2件
- 一方 `pain_level>=2` の困りごとは109件ある。痛みの量に対して支払い意思が2桁少ない
- `fabrication` ドメインは痛み率44%（3ドメイン中で突出、keywords.yaml 2026-08-03の実測）だが、`monetizable=true` は2件で、うち1件は「既存製品の買い替え」であり `service_candidate` と一致しない

原因は収集元の性質にある。SNS・技術フォーラムに現れるのは無料文化の層であり、「金を払う側」の発話ではない。`domains.yaml` が `inference_placement` について「想定顧客は守秘義務があり業務上の悩みを公開SNSに書かない。本基盤では検証できない」と既に記録した問題が、他ドメインにも及んでいる。

**求人・案件は支払い意思そのものである。** 企業が予算を付けて人を探している領域は、その領域に金が動いている直接の証拠になる。`maritime-collector` では `hiring maritime` キーワードで競合6社（Saildrone・Saronic・Spire Global・Greywing・Nautilus Labs・Arundo）を発見済みで、手法としては検証されている。ただし同レポートが「個人の困りごとではなく市場投資の裏付け・競合発見シグナルとして役割を分けて運用する」と明記したとおり、需要シグナルとは役割が違う。

なお `sns-collector` 側の既存キーワードでは求人は**ノイズとして扱われていた**。`"model accuracy" edge` の16件中11件（69%）が求人スレッドへの定型応募コメントで、これが痛み率0%の主因だった（keywords.yaml 2026-08-08の実測）。同じデータを、役割を変えて正面から使う。

選定基準はADR-0006・ADR-0009を引き継ぐ（認証要否 / 既存アーキテクチャとの適合 / 対象領域との重なり）。

### 検討した選択肢

| 案 | 却下理由 |
|---|---|
| Hacker Newsの月次求人・案件スレッド（Algolia検索API） | 採用。認証不要で既存の`common/http.py`に乗る。スレッド直下のコメントが1件1求人という構造を持ち、企業名・職種・勤務地・給与が定型で並ぶ。`hackernews`用のAlgoliaクライアントと同じAPIのため新しい通信の作法が増えない |
| 既存`hackernews`コレクタへ求人キーワードを足す | 却下。Algoliaの全文検索は「求人スレッドの中だけ」を指定できないため、求人票かどうかを判別できない。加えて`extract`の抽出プロンプトは困りごとを取る前提で書かれており、同じ`platform`に混ぜると`insight_type`・`pain_level`の分布が汚れる。役割が違うものは別プラットフォームに分ける |
| RemoteOK API / We Work Remotely RSS | 本ADRでは扱わない。求人媒体としては素直だが、掲載は「その企業が採用中」以上の情報を持たず、Hacker Newsのような一次記述（技術スタック・課題・給与レンジ）が薄い。Hacker News側の実測後に必要なら検討する |
| ランサーズ・クラウドワークス・ココナラ（日本語圏の案件） | 却下。公開APIが無く、取得手段がスクレイピングに限られる。各社の利用規約が自動取得を禁じており、規約に反する収集経路を本基盤へ持ち込まない。**日本語圏の案件相場は本基盤の対象外**とし、必要な場合は人手の調査で補う |
| Upwork API | 却下。APIキー発行に事業者審査があり、ADR-0005が不利益として挙げた「鍵の管理範囲が広がる」に加えて審査という人手の外部作業が入る。得られる情報量に対して初期コストが見合わない |

## 決定

**Hacker Newsの月次求人・案件スレッド（`Ask HN: Who is hiring?` / `Ask HN: Freelancer? Seeking freelancer?`）を、6つ目の収集プラットフォーム `hnjobs` として追加する。役割は需要シグナルではなく金の流れシグナルとし、既存の5プラットフォームとは別の`platform`値で保存する。抽出（`extract prepare`）の既定対象には含めない。**

判断の根拠:

1. **支払い意思の観測は、収集元の追加でしか解消しない。** キーワードを何度改訂しても、SNSに現れない層の発話は取れない。ADR-0009がGitHub/Redditを足したのは「困りごとの一人称表現」の量を増やすためだったが、量を増やしても`monetizable`が増えない構造は変わらない。観測する対象そのものを変える
2. **役割が違うものを同じ`platform`に混ぜない。** 求人票には困りごと表現が構造的に含まれない。既存の`hackernews`へキーワードとして足すと、痛み率という既存の判定指標が意味を失う（2026-08-08の実測で69%の求人混入が痛み率0%を招いた前例がある）。`platform='hnjobs'`として分ければ、レポート・`keywords quality`の集計を役割ごとに引ける
3. **スレッド起点の2段階取得を採る。** 「投稿者でスレッドを引き、タイトルで種別を分け、スレッド内をキーワードで検索する」。全文検索では求人スレッドを狙い撃ちできず、タイトルの全文検索では別人の類似スレッドが混ざる（`Show HN: HN Hiring - Search and Filter Who Is Hiring`）。既存の「キーワード→検索→JSONL→DB」の型からは外れるが、外れるのは検索対象の決め方だけで、保存・重複判定・失敗隔離は既存と同一構造にした
4. **スレッド直下のコメントだけを求人票とみなす。** 月次スレッドは「トップレベル＝1件の求人票、その下＝質問・議論」という運用で回っている。返信まで採ると `Incorrect.` のような断片がDBへ入る。深さは`parent_id`と`story_id`の一致で判別できるため、コードに固定した（設定にしない）
5. **既定の抽出対象には含めない。** ADR-0009と同じ判断。求人票はBluesky投稿より1〜2桁長く、未検証のまま既定バッチへ混ぜると課金される抽出セッションのコンテキストを圧迫する。加えて既存の抽出プロンプトは困りごとを取る前提で書かれており、求人票用のプロンプトはまだ無い

## 結果

### 実装した内容

- `src/sns_collector/hnjobs/`（`client.py` / `models.py` / `search.py`）を追加した。保存・重複判定・失敗隔離の構造は既存プラットフォームと同一
- `db/adapters.py`に`from_hnjobs`を追加した。**スキーマ変更（マイグレーション）は不要**（`platform`列はVARCHARでCHECK制約を持たない。ADR-0006・ADR-0009と同じ結論）。求人か案件かの区別は`metrics`のJSONへ`thread_kind`として持つ
- `hackernews/models.py`の`_clean_html`を`clean_html`へ公開名に変えて共有した。同じAlgolia APIのHTML断片を扱うため、複製すると片方だけ直す事故が起きる。既存の呼び出しは同ファイル内2箇所のみ
- `config/keywords.yaml`に`hnjobs:`セクション（9キーワード）を追加した。実測値と却下理由は同ファイルの改訂履歴にある
- `extract/prepare.py`の既定対象は変更していない（ADR-0009「実装した内容」に挙げた値のまま）

### 実装中に判明した、収集の質に直結する3点

- **Algoliaの既定のタイプミス吸収が、短い語を無関係な語へ広げていた。** `"cnc"`は求人スレッドで13件ヒットしたが、中身は不動産・請負業者のマッチングサービス等で、工作機械と関係するものは1件も無かった。`typoTolerance=false`で0件になる。`hnjobs/client.py`で無効化した。**既存の`hackernews`側は既定のままである**（あちらは痛み率で質を測っており、無効化の影響を測り直す作業が別途要る。本ADRのスコープ外）
- **案件スレッドは金の流れシグナルとして機能しない。** `Ask HN: Freelancer? Seeking freelancer?` は発注側（`SEEKING FREELANCER`）と受注側（`SEEKING WORK`）の両方が投稿する場だが、2026年8月のスレッドはトップレベル14件**すべてが受注側**で、発注側は0件だった。区別せずに数えると「案件が14件ある」と読み違える。`posts.metrics`へ`seeking`を記録して分離できるようにし、スレッド自体は供給側（どの技術で個人が受注しているか）の観測として役割を変えて残した。求人スレッド側は全件が発注側のため名乗りが無く、`seeking`は常に`null`になる
- **案件スレッドの主催アカウントは引き継ぎで変わる。** 求人・求職スレッドは`whoishiring`だが、案件スレッドは2025年まで`whoishiring`、2026年1月から`jon_north`が立てている。単一アカウントに固定する実装だと、引き継ぎの月から案件側だけが静かに0件になる。種別ごとに複数アカウントを持つ形にし、種別ごとの取得件数が0件のときは警告を出すようにした

### 得られた最初の判定材料

`fabrication`ドメイン（3Dプリンタ・機構設計）の求人・案件は**0件**だった（`"3d printing"` `"cnc"`とも求人3本・案件3本で0）。SNS側では痛み率44%と3ドメイン中で突出していた領域に、企業の予算が1件も観測できない。「痛みはあるが誰も金を払っていない」という、需要シグナルだけでは弾けない状態を示す最初の実測値である。この1点だけでも収集元を分けた価値がある。

### レビューで判明した、静かな0件の再発経路（2026-08-11 追記）

主催アカウントの引き継ぎ（上記）を塞いだ後も、同じ「気づけないまま0件」に至る経路が2つ残っていた。どちらも `adapter/source/hnjobs/source.py` で対処した。

- **スレッドの枠を、取得したアカウントの順で埋めていた。** 案件スレッドは旧ホストの投稿にも残っているため、`thread_limit` を増やすと旧ホストの2025年分が先に枠を取り、現行ホストの2026年分が落ちる。枠は `created_at` の新しい順で埋める
- **主催アカウントの投稿を見る窓を、月次スレッドの本数から算出していた。** 現行ホストは個人アカウントであり、月次スレッド以外の投稿が混ざると目的のスレッドが窓の外へ出る。窓は固定（50件）にした。`hitsPerPage` は1リクエストなので広げてもコストは変わらない

### 受け入れる不利益

- **同じコメントが`hackernews`と`hnjobs`の両方に入りうる。** `posts.id`は`platform:native_id`のため別レコードとして共存する。プラットフォーム横断で件数を数える集計は二重計上になる。既存のレポートは`platform`別に集計しているため現状の影響は無いが、横断集計を足すときはここを意識する必要がある
- **収集の所要時間が長い。** スレッド数×キーワード数のリクエストになる（既定で6スレッド×9キーワード＝54回）。`common/http.py`の1秒ペーシングで約1分。キーワードを増やすと線形に伸びる
- **求人票用の抽出プロンプトが無い。** 現状は収集してDBへ入れるところまでで、構造化抽出はできない。`insight_type`（complaint/need/workaround/advantage）の語彙は求人票に合わない
- **英語圏・技術職に偏る。** Hacker Newsの求人はUS中心のソフトウェア職であり、日本語圏の案件・製造業の求人は観測できない

### 未解決のまま残る事項

- **初回収集後のキーワード検証。** 現在の実測値は検索APIでの事前確認であり、収集データでの評価はまだ無い（ADR-0006・ADR-0009と同じ段階）
- **求人票を構造化する手段。** 抽出プロンプト（会社・職種・技術スタック・給与レンジ・リモート可否）を書くか、`insights`とは別テーブルにするかを決めていない。決めるまでは`extraction_status='pending'`のまま溜まる
- `maritime-collector/config/keywords.yaml`への`hnjobs:`セクション追加は行っていない。あちらは`hackernews`側の`hiring maritime`で同種の情報を既に取れているため、移行するかは実測後に判断する
- `scripts/cron_run.sh`のusage文字列・`case`分岐への追記、crontabへの実登録は行っていない。ADR-0009の`github`/`reddit`と同じく、キーワード検証後の運用作業として残る
- 既存`hackernews`の`typoTolerance`は既定のまま。無効化すると既存キーワードの実測値（件数・痛み率）が変わるため、変更するなら再測定とセットで行う
