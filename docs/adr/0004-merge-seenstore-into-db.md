# ADR-0004: SeenStore を廃止し、重複排除をDBへ統合する

- ステータス: 採用
- 日付: 2026-07-28
- 関連: [requirements.md](../requirements.md) F-03 / [design.md](../design.md) §3.1, §4.2

## 背景

現状、run跨ぎの重複収集を防ぐため `SeenStore`（`state/{platform}_seen.json`）が既知の投稿IDを保持している。60日を過ぎたエントリは自動的に破棄される。

DBを導入すると、同じ「この投稿は既知か」という判定を2箇所が独立に持つことになる。issue #3でも統合の可否が検討事項に挙がっていた。

## 決定

**`SeenStore` を廃止し、重複判定を `posts` テーブルの主キー制約に一本化する。**

## 理由

1. **単一の真実源になる。** 二重管理は必ず乖離する。SeenStoreにあってDBにない、あるいはその逆の状態が発生すると、原因の切り分けが難しい。
2. **60日プルーニングの制約が消える。** SeenStoreはファイルサイズ肥大を防ぐため60日で破棄していた。DBなら全期間の投稿IDを保持でき、61日後に同じ投稿を再取得してしまう問題がなくなる。
3. **ロードが冪等になる。** `INSERT OR IGNORE` により、同一JSONLを何度ロードしても結果が変わらない（F-01）。
4. **状態ファイルの原子的書き込みが不要になる。** SeenStoreは一時ファイル＋`os.replace` で原子性を担保していた。DBのトランザクションがこれを代替する。

## トレードオフ

**収集コマンドがDBに依存するようになる。** これまで収集はJSONL書き出しのみで完結していた。

これを受け入れる根拠:

- DuckDBは組み込み型で、常駐プロセスを必要としない（ADR-0001）
- 生JSONLの書き出しは維持するため、DBが破損しても生データは失われない（F-04）
- 収集と分析を同一マシンで動かす前提であり、DB不在という状況が実質的に発生しない

## 移行

1. 既存の `state/{platform}_seen.json` を読み、投稿IDのみを持つ行として `posts` へ投入する（`extraction_status='skipped'`、本文なし）

   → 本文が無いため抽出対象にはならないが、重複判定は機能する。実際にはPhase 0開始時点で収集データが存在しないため、この移行は不要になる見込み。

2. `state/*_seen.json` を削除する
3. `common/seen_store.py` とその単体テストを削除する
4. 収集コマンドから `SeenStore` の参照を除去し、DBの既知ID照会へ置き換える

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| SeenStoreを維持し、DBと二重管理 | 乖離が発生し、原因追跡が困難になる |
| SeenStoreを維持し、DBは分析専用 | 収集時のDB書き込みが遅れ、「収集済みだがDBにない」期間が生じる。ロードの冪等性も別途担保が必要 |
| 収集時にDBへ直接書き、JSONLを廃止 | 生データが失われる。DB破損時に復旧できない（F-04違反） |
