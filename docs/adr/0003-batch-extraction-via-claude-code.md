# ADR-0003: 構造化抽出は Claude Code セッション経由のバッチ方式とする

- ステータス: 採用
- 日付: 2026-07-28
- 関連: [requirements.md](../requirements.md) N-03, N-04 / [design.md](../design.md) §1.2, §4.3

## コンテキスト

投稿本文から潜在ニーズ・不満・製品優位性を抽出するには、自然言語の意味理解が要る。ルールベースでは「面倒」「だるい」「毎回やってる」といった多様な表現を、意味のある区分へ落とし込めない。

一方で、パイプラインからLLM APIを直接呼ぶと以下が発生する。

- APIキーの管理と従量課金（サブスクリプション契約の範囲を超える）
- パイプラインのテストがLLMに依存し、単体テストが書きにくくなる
- 抽出結果の再現性・監査可能性が低下する

### 検討した選択肢

| 案 | 却下理由 |
|---|---|
| パイプラインからClaude APIを直接呼ぶ | 従量課金が発生し、契約プラン内という制約を満たさない（N-04） |
| ローカルLLM（Ollama等）で抽出 | 制約は満たすが、日本語の微妙なニュアンス判定で品質が劣る。実行環境のGPU有無にも依存する。将来の選択肢として残す |
| ルールベース抽出 | 表現の多様性を吸収できず、`insight_type` や `pain_level` の判定が機能しない |
| 抽出せず全文検索のみ | 構造化された絞り込み・集計（F-09, F-14）が成立しない |

## 決定

**パイプライン本体からLLMを一切呼ばない。抽出はClaude Codeセッションが担い、パイプラインは「バッチを書き出す」「結果を検証して取り込む」のみを行う。**

```
extract prepare（自動） → batch.jsonl + batch.md
                              ↓
                    Claude Code セッション（手動起動）
                              ↓
                        batch.result.jsonl
                              ↓
              extract load（自動・スキーマ検証あり）
```

判断の根拠:

1. **契約プランの範囲に構造的に収まる。** パイプラインにLLM呼び出しが存在しないため、追加の従量課金が発生する経路がない（N-04）。
2. **パイプライン全体がテスト可能になる。** バッチ生成・スキーマ検証・DB投入はすべて決定論的で、通常の単体テストで検証できる。
3. **抽出結果が監査可能。** 入力バッチと出力結果がファイルとして残るため、いつ・何を・どのプロンプトバージョンで抽出したかを後から追跡できる（N-05）。
4. **抽出ロジックの改善サイクルが速い。** プロンプトはMarkdownファイルであり、小バッチで試して即座に改訂できる。コードのデプロイを伴わない。
5. **実装の差し替えが容易。** バッチの入出力形式が契約になっているため、将来ローカルLLMやAPIへ移行する場合も、その部分だけを置き換えればよい。

## 結果

### 抽出が完全自動にならない

週1回程度、Claude Codeセッションを手動で開いてバッチを処理する運用が発生する。これを受け入れる根拠:

- 抽出は「一度だけ推論して凍結する」設計であり、頻度が低い（1投稿につき1回）
- 収集・ロード・埋め込み・レポート生成はすべて完全自動のまま
- 契約プラン内という制約を満たす他の手段が現時点でない

緩和策として、1バッチの所要時間が15分以内に収まる件数をPhase 2で実測し、運用が継続可能な水準に調整する。

### 外部送信ポリシーが変わる

この方式では**投稿本文がAnthropicへ送信される**。issue #2/#3で掲げた「外部への送信・公開はしない」から方針が変わるため、[requirements.md](../requirements.md) §5に変更点を明記し、issue #3へコメントとして記録する。

対象データはいずれも公開SNS上の公開投稿であり、非公開情報を含まない。なお、埋め込み生成は引き続きローカルで完結させる（ADR-0002）。

### CIでのPRレビューは試して撤回した（2026-08-02 追記）

PRレビューをCIでヘッドレス実行できないか検証し（issue #30）、**動作はしたが撤回した。** この決定を残すのは、同じ検討を繰り返さないためである。

**撤回の理由は課金区分である。** この ADR は「パイプラインからLLMを呼ばない」ことで追加課金の経路を構造的に作らない、としている。CIレビューはその外側（GitHub Actions）にあるため抵触しないと考えたが、実測は違った。

| 実測値 | |
|---|---|
| 1回のレビュー | 13ターン / 9分50秒 / $5.39相当 |
| 課金先 | 対話セッションの定額枠ではなく**利用クレジット**（メーター課金） |
| 当時の残高 | プロモーションクレジット $81.30（2026-09-19 失効） |

**残高で賄えるのは約15回**で、しかも期限付きだった。手元の対話セッションで `/code-review` を実行すれば同じレビューが定額枠に収まるため、CI化は「込み」の使用量をメーター課金へ変換しているだけであり、支出面では純粋な損である。

副次的に、送信対象の線引きも動かさずに済んだ。CIレビューはPRの差分（＝リポジトリのソース）をAnthropicへ渡す新しい経路になるはずだったが、撤回により**外部へ渡るのは構造化抽出の投稿本文だけ**という当初の線引きが維持される。

検証の過程で分かった、再挑戦する場合に効く事実:

- アクションはワークフローファイルがデフォルトブランチと一致しないPRでは、失敗ではなく成功として自らスキップする。終了状態だけを見ると「走っていないのに緑」になる
- `claude setup-token` のOAuthトークンは短命という報告があり、CI用途では失効の運用が要る
- 指摘0件のとき、アクションはPRへ何も残さない。「走って指摘なし」と「走っていない」をPRから区別できない

未解決のまま残る事項: レビュー実行が人の記憶に依存する状態へ戻る。`required_review_thread_resolution` はコメントが1件も無いPRを止められないため、ここは機械化できていない。

### LLM出力の機械検証が必須になる

LLMの出力は信頼せず、DBへ入る前に機械的に検証する。

- 必須フィールドの存在
- 列挙値の妥当性（`insight_type`、`domain`）
- 数値の範囲（`pain_level` 0〜3、`confidence` 0.0〜1.0）
- `post_id` が当該バッチに含まれていたかの照合（ハルシネーション検出）
- 重複行の排除

検証を通らなかった行は拒否し、`errors.jsonl` へ隔離する。該当投稿は未抽出状態のまま残し、次回バッチの対象とする。
