# ADR-0011: 4層構造と層間のimport規則を定め、機械検査で強制する

- ステータス: 採用
- 日付: 2026-08-11
- 関連: [ADR-0003](./0003-batch-extraction-via-claude-code.md) / [ADR-0004](./0004-merge-seenstore-into-db.md) / [ADR-0009](./0009-add-github-and-reddit-demand-signal-sources.md) / [ADR-0010](./0010-add-hackernews-jobs-money-signal-source.md) / [design.md](../design.md)

## コンテキスト

`sns_collector` は収集元を1つ追加するたびに `client.py` / `models.py` / `search.py` の3点セットを複製してきた（ADR-0006・ADR-0009・ADR-0010）。ADR-0009 は「それ以外は既存3プラットフォームと同一構造の複製である」と明記しており、複製は意図的な選択だった。プラットフォームが6つになった時点で、この選択の代償が測れる形で現れている。

依存関係を機械的に抽出した結果（2026-08-11時点、`src/sns_collector` 配下40ファイル）:

- **`*/search.py` 6ファイルが、収集ユースケースとI/Oを同居させている。** 1ファイルあたり96〜174行、合計711行。HTTP呼び出し・JSONL書き込み・DB投入・進捗の`print`・失敗隔離がすべて同じ関数にある。**6ファイルの制御構造はほぼ同一で、違うのは呼ぶクライアントとDTOだけである**
- **ユースケースに相当する13モジュールが `duckdb` / `requests` に直接依存している。** `report` `graph` `embed` `search` `keyword_quality` `extract.*` を含む
- **テストが `unittest.mock.patch` に依存している。** 収集処理を単体で動かす手段が無く、`patch("...search.search_items")` のようにモジュール属性を差し替えるしかない。ADR-0009 が `COLLECTORS` に「関数を直接束ねない。モジュールを持つ」という制約を課したのも、この patch 手法と噛み合わせるためだった。**テスト手法の都合が本番コードの構造を規定している**
- **プラットフォーム間の水平依存が生まれた。** ADR-0010 で `hnjobs/models.py` が `hackernews/models.py` の `clean_html` を import した。同じAlgolia APIを読むため複製を避けた判断だが、6つの兄弟パッケージが互いを参照し始める入口になっている

加えて、ADR-0010 の実装中に「`common/config.py` でバリデーションすると common が上位モジュールを import することになる」ため、検証処理を `hnjobs/search.py` の冒頭へ逃がした。これは層の境界が定義されていないために、その場しのぎで置き場所を決めた例である。

この基盤は「週末のみ保守できる個人開発」という制約下で長期運用する。収集元は今後も増える。**増やすたびに700行の複製が800行、900行になる構造を、増える前に断つ必要がある。**

### 検討した選択肢

| 案 | 却下理由 |
|---|---|
| 4層（domain / usecase / adapter / entrypoint）+ 関数引数による依存注入 | 採用。依存の向きを一方向に固定するというClean Architectureの核心を得つつ、抽象基底クラス・Protocol・DIコンテナを導入しない。Pythonでは関数がそのままポートとして渡せる |
| `typing.Protocol` でポートを定義する | 却下。ADR-0009 が同じ判断を既にしている（「型チェッカーが無くCIも`ruff`+`pytest`のみのため、Protocolを書いても実行時に検証されずドキュメント価値のみになる」）。この状況は変わっていない。mypy/pyright の導入は別の決定であり、それ抜きにProtocolだけ入れると「守られているように見えて検証されていない規約」が増える |
| 3層（domain / infrastructure / entrypoint）へ簡略化する | 却下。現状の違反27件の大半が「違反でなくなる」だけで、`search.py` の重複も `duckdb` への直結も残る。層を分ける目的は境界に名前を付けることではなく、**ユースケースを単体で実行可能にすること**にある |
| 現状維持（複製を続ける） | 却下。収集元7つ目で複製は830行に達する。ADR-0009 が「新しい抽象化は、この機能が実際に持ち込んだ構造差にのみ対応させる」と述べた方針は、差が出るまで待つ判断として妥当だったが、6つ揃って差が「クライアントとDTOだけ」と確定した |
| ヘキサゴナル/オニオン等の別名の同型構造 | 本ADRでは扱わない。依存の向きを内向き一方向に固定する点で本質は同じであり、名前の選択に実利が無い |

## 決定

**`sns_collector` を domain / usecase / adapter / entrypoint の4層に分け、層をディレクトリで表現し、層間のimportを下表の規則で制限する。規則は `scripts/check-layer-deps.sh` が機械的に検査し、pre-commit と CI で強制する。**

### 層とディレクトリ

```
src/sns_collector/
  domain/       中核の型と純粋なルール
  usecase/      ユースケース。I/Oは引数で受け取る
  adapter/      外部世界との境界
    http.py jsonl.py config_file.py text.py  ← 共通基盤
    db/                                       ← DuckDBに触るもの
    source/<platform>/                        ← 収集元ごと
  entrypoint/   CLI。依存を結線する
```

**`usecase` に置くのは「複数のI/Oを手順として組み合わせる処理」に限る。** 単一のクエリやトランザクションが処理の本体であるもの（レポートの集計、意味検索、埋め込み、グラフ導出、抽出バッチの作成と取り込み）は `adapter/db/` に置く。これらはSQLが8〜13箇所あり、無理に2層へ割ると `usecase` 側には引数を渡し替えるだけの関数が残る。抽象化のための抽象化になり、層を分ける目的（ユースケースを単体で実行可能にすること）に寄与しない。

ただし、そこから**純粋な判定・整形が切り出せる場合は `usecase` へ出す**。`keyword_quality` がその例で、SQLは `adapter/db/queries.py`、痛み表現の判定は `usecase/keyword_quality.py` にある。判定ロジックのテストはDBファイル無しで書ける。

### import規則

行が「importする側」、列が「importされる側」。

| ↓from \ to→ | domain | usecase | adapter | entrypoint |
|---|---|---|---|---|
| **domain** | 可（同層内） | **不可** | **不可** | **不可** |
| **usecase** | 可 | 可（同層内） | **不可** | **不可** |
| **adapter** | 可 | **不可** | 可（制限あり。下記） | **不可** |
| **entrypoint** | 可 | 可 | 可 | 可（同層内） |

`adapter` 層内には追加の規則を置く。

- `adapter/source/<A>` から `adapter/source/<B>` へのimportは**不可**（兄弟の収集元は互いを知らない）
- `adapter/source/*` から `adapter/http.py` `adapter/jsonl.py` `adapter/db/` 等の共通基盤へのimportは**可**
- 共通基盤から `adapter/source/*` へのimportは**不可**

外部ライブラリにも同じ考え方を適用する。

| 層 | 使ってよい外部ライブラリ |
|---|---|
| domain | 標準ライブラリのみ |
| usecase | 標準ライブラリのみ |
| adapter | 制限なし（`requests` `duckdb` `yaml` `dotenv` 等） |
| entrypoint | 制限なし |

判断の根拠:

1. **`usecase` から `duckdb` と `requests` を締め出すことが、この決定の実質である。** 層の名前や図ではなく、この1点が「ユースケースを単体で実行できる」状態を作る。収集ロジックのテストが、HTTPサーバもDBファイルも `patch` も無しで書けるようになる
2. **依存逆転は関数引数で行う。** `usecase` は必要なI/Oを引数で受け取り、`entrypoint` が実装を渡す。Pythonの関数はそれ自体が単一メソッドのインターフェースであり、抽象基底クラスを挟む必要が無い。テストでは素の関数を渡せばよく、`patch` によるモジュール属性の差し替えが不要になる
3. **層はディレクトリで表現する。** モジュール名と層の対応表を別ファイルに持つと二重管理になり、実装と表が食い違う。ディレクトリなら構造そのものが層を語り、検査もパスから機械的に判定できる（このリポジトリの「規約は1箇所にしか書かない」に従う）
4. **兄弟の収集元は互いを知らない。** ADR-0010 で作った `hnjobs → hackernews` の依存は、この規則の下では違反になる。共有したいものは共通基盤へ引き上げる。6つの収集元が互いを参照し始めると、1つの変更が他5つへ波及する
5. **規則は文字列と構造で判定できるため、承認フローではなく機械検査に落とす。** ルートの `CLAUDE.md` が定めた使い分け（「文字列で判定できるものは検査に、できないものは人への確認に落とす」）に従う。import の可否は意図を読む必要が無い

## 結果

### 実装した内容

- `usecase/collect.py` 1ファイルが、6つの収集元すべての収集手順を担う。`adapter/source/<platform>/source.py` は「何を検索するか」を `CollectTask` の列にして返すだけになった。hnjobs の2重ループ（スレッド×キーワード）も、タスクの直積として同じ手順に乗る
- `adapter/http.py` に `source_errors()` を置き、`requests` の例外を `domain` の `SourceUnavailable` へ変換する。`usecase` は `requests` を import できないため、この形でしか失敗を受け取れない
- ADR-0010 で作った `hnjobs → hackernews` の水平依存は、共有していた `clean_html` を `adapter/text.py` へ引き上げて解消した
- 収集元ごとに6ファイルへ書き写されていたテストを `tests/test_collect.py` へ統合した。DBもHTTPも `patch` も出てこない
- `scripts/check-layer-deps.sh` が規則を検査する。実装は Python（`ast`）だが、外部依存を増やさないようスクリプト内に埋め込んでいる

### 得られるもの

- **収集ユースケースが1つに統合される。** 6ファイル711行の複製が `usecase/collect.py` 1ファイルになる。収集元の追加は「クライアントとDTOを書き、`entrypoint` で結線する」だけになり、失敗隔離・保存順序・重複判定のロジックを複製しなくなる
- **`sns-collector/CLAUDE.md` が定める3層の失敗モード対策（キーワード単位の保存 / HTTP失敗の隔離 / パース失敗の隔離）が1箇所に集まる。** 現在は6ファイルに同じ対策が書き写されており、7つ目を追加する人がどれか1つを落とす余地がある。「この失敗モードは機械的に検出できない。実装時とレビュー時に人が見るしかない」と同ファイルが書いているのは、複製されているためである
- **テストから `patch` が消える。** ユースケースには素の関数を渡す

### 受け入れる不利益

- **移行が大きい。** 実装40ファイル・テスト24ファイルが対象で、ほぼ全ファイルのimport文が変わる。1回のPRで完了させる（部分適用の状態を残すと、どちらの規則で書けばよいか分からない期間が生まれる）
- **`entrypoint` が太る。** 依存の結線先が集中するため、`cli.py` の責務が「引数解析 + 結線 + 表示」になる。層としては正しいが、ファイルは長くなる
- **引数の数が増える。** ユースケース関数がI/Oを引数で受けるため、呼び出し側の記述量は増える。`frozen=True` のdataclassにまとめて渡すことで緩和するが、消えはしない
- **静的型による保証は無い。** 注入する関数のシグネチャが合っているかは実行時にしか分からない（Protocolを入れない選択の代償）。テストで担保する
- **ADR-0009 が `COLLECTORS` に課した制約（「モジュールを持つ。関数を直接束ねない」）は、その理由（patchとの噛み合わせ）ごと不要になる。** 同ADRの決定を覆すものではなく、前提が変わったことによる自然な解消として扱う

### 適用範囲

本ADRは `sns-collector` に適用する。`dashboard` は既に `app` / `cli` / `paths` / `sources/*` に分かれており、`sources/*` が読み取りアダプタとして機能している。同じ規則を当てはめる価値はあるが、規模が小さく（7ファイル）現状で境界が壊れていないため、本ADRでは対象としない。将来 `dashboard` が複雑化したときに、本ADRの規則をそのまま適用できる。

### 未解決のまま残る事項

- **`maritime-collector` は `sns-collector` のCLIを設定だけ変えて再利用する（ADR-0008）。** 本ADRの再編で `sns_collector` パッケージの内部構造は変わるが、CLIの呼び出し形（`uv run --project ../sns-collector sns-collector bluesky ...`）は変えない。cronラッパーへの影響は無い
- 静的型チェッカー（mypy/pyright）の導入は本ADRでは決めない。導入すれば注入する関数のシグネチャを検証できるようになり、Protocol の再検討にも繋がるが、CIの実行時間と設定の維持コストを別途評価する必要がある
- `domain` 層に何を置くかの線引きは、移行の実作業で確定する。収集元ごとのDTO（`BlueskyPost` 等）は外部APIの形に対応する構造であり `adapter` に置くが、DBの共通形（`PostRow`）と抽出結果（`Insight`）は `domain` に置く
