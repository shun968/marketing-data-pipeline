# ADR-0001: 分析ストアに DuckDB を採用する

- ステータス: 採用
- 日付: 2026-07-28
- 関連: [design.md](../design.md) §3, §4.5

## 背景

issue #3では永続化層の選択肢としてリレーショナル（SQLite等）、ベクトルDB（Chroma / LanceDB / Qdrant）、グラフDB（Neo4j / Kùzu）が挙がっていた。本基盤には3種すべての要素がある。

- 期間・ドメイン・痛み強度での絞り込み → リレーショナル
- 表記揺れを跨いだ意味検索 → ベクトル
- アカウント・キーワード・製品の関係探索 → グラフ

素直に読むと3種のストアが必要に見えるが、個人開発でローカル運用する規模（年間10万件想定）に対して3つのデータストアを同期させる運用コストは見合わない。

## 決定

**DuckDB を単一の分析ストアとし、VSS拡張でベクトル検索を賄う。グラフは汎用エッジテーブルで表現する。**

## 理由

1. **SQLとベクトル検索が同一クエリ内で合成できる。** 「直近30日のドメインXで、痛み強度3以上、かつ『決済の手間』に意味的に近い投稿」という問い合わせが1本のSQLで書ける。ストアが分かれていると、アプリケーション側でID集合を突き合わせる実装が必要になる。
2. **常駐プロセスが不要（N-08）。** 単一ファイル・組み込み型で、DBサーバの起動・管理が発生しない。
3. **バックアップと移設がファイルコピーで完結する（N-07）。**
4. **分析ワークロードに適した列指向。** 集計中心の用途でSQLiteより有利。
5. **LIST / JSON 型を第一級で扱える。** `matched_keywords` や `competitors` を中間テーブルなしで表現でき、スキーマが単純になる。
6. **グラフ探索の要求が浅い。** 本基盤で必要なのは1〜2ホップの近傍探索と共起集計であり、再帰CTEで十分に書ける。多段の経路探索を要求していない。

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| SQLite + Chroma/LanceDB | ストアが2つに分かれ、SQL絞り込みとベクトル検索を合成できない。同期の責務がアプリ側に漏れる |
| Chroma / Qdrant 単体 | 集計・時系列分析が弱い。レポート生成の要件（F-14）を満たしにくい |
| Neo4j / Kùzu の併用 | 現時点で多段グラフ探索の要求がない。運用コストが便益を上回る |
| PostgreSQL + pgvector | 常駐プロセスが必要（N-08違反）。個人利用のローカル運用に対して重い |

## 結果

- 単一ファイル `data/analysis.duckdb` にすべてが収まる
- VSS拡張のHNSWインデックス永続化に制約がある可能性があるため、Phase 3で挙動を検証する。10万件規模なら総当たり計算でも許容範囲であり、これを既定とする
- 将来、多段グラフ探索が実際にボトルネックになった場合は、`edges` テーブルを起点に専用グラフDBへエクスポートする経路を取る。現時点では導入しない
