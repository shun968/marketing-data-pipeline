# ADR-0012: APIキーを隔離境界の外へ置き、ワークスペース内に持たない

- ステータス: 採用
- 日付: 2026-08-16
- 関連: docs/isolation.md（制御の層と経路） / ADR-0007（隔離境界をdevcontainerで実現する） / ADR-0003（Claude Codeセッションの役割）

## コンテキスト

`.claude/settings.json` は `.env` の読み書きを deny しているが、これはツール層の制御点であり、Bashが起動した子プロセスには効かない（docs/isolation.md §3 経路3）。この境界の状態を実測した。

| 確かめたこと | 結果 |
|---|---|
| deny対象パスを `python3` の子プロセスから開く | 素通りで内容が読める |
| コンテナ内から非許可ホスト（example.com:443）へ接続 | 到達不可（iptables default-deny） |
| コンテナ内から `api.anthropic.com:443` へ接続 | 到達可 |
| `unshare -Urm` による非特権user namespace作成 | `Operation not permitted` |

経路3を塞ぐOS層はBashサンドボックス（bubblewrap）だが、`kernel.apparmor_restrict_unprivileged_userns=1` はホスト全体に効き、コンテナのプロセスは `docker-default` プロファイル下で `userns create` を持たない。**devcontainerの内側でも起動できない。** ADR-0007はホスト直起動を前提に同じ結論へ達しており、コンテナ内でも変わらないことをここで確認した。

一方で `sns-collector/.env` には YouTube APIキー・GitHubトークン・Redditのクライアントシークレットが実在し、ワークスペースはコンテナへbindマウントされている。ファイアウォールが到達を許す唯一の宛先は `api.anthropic.com`、すなわちセッションが文脈を送る先そのものである。したがって残るリスクは任意の持ち出しではなく、**鍵がトランスクリプトに載ってAnthropicへ送信されること**である。これはADR-0002・ADR-0003で引いた「外部APIへ送るのは構造化抽出の投稿本文だけ」という線を、意図せず越える経路になる。

### 検討した選択肢

| 案 | 却下理由 |
|---|---|
| bubblewrapを導入して `sandbox.enabled` を有効化する | 上記のとおりコンテナ内でも起動できない。入れても警告を出して素通りし、守れているという誤解だけが残る |
| コンテナへ `--cap-add=SYS_ADMIN` を与えてsandboxを動かす | コンテナ内でrootが取れ、iptablesを消せる。境界の実体を壊して内側に別の境界を作ることになる |
| このコンテナ専用のAppArmorプロファイルをホストへ追加する | ADR-0007が拒否したホストへの変更であり、緩めるのは境界にしたいコンテナ自身である |
| 収集専用uidを作り、固定ラッパーだけを sudo 可にする | 経路3・4を塞げるが、ラッパーが新しい信頼境界になり、出力ディレクトリの権限設計も要る。定期収集がホスト側cronで完結している以上（ADR-0007）、コンテナ内に鍵を置く前提を維持するためだけの機構になる |
| PreToolUse hookでコマンド文字列を検査する | 制御点の追加であって境界ではない。`python -c` の中身は文字列から追えず、誤検知でゲートごと無効化される |

## 決定

**APIキーを持つ環境ファイルをワークスペースの外に置き、場所は `SNS_COLLECTOR_ENV_FILE` で明示的に受け取る。** 既定は**ホスト側の** `~/.config/sns-collector/.env`（`sns-collector/scripts/cron_run.sh` がexportする）。devcontainer内のホームは対象外である。`.claude` / `.config/gh` 以外は再作成で消えるうえ、そこへ永続化すれば境界の内側に鍵を常設することになり、この決定の目的を打ち消す。

判断の根拠:

1. **塞げない経路の側ではなく、置き場所の側を変える。** 経路3を塞ぐOS層はこの機械では成立しない。読まれるファイルが境界の内側に無ければ、経路3も経路4（hooks・MCP）も同時に無効になる。境界を1段増やすより副作用が小さい。
2. **暗黙の探索をやめる。** `load_dotenv(dotenv_path=None)` はカレントから上へ `.env` を探すため、ワークスペース内へ鍵を置く運用を誘発する。場所を環境変数で受け取り、指定が無ければ探索しない。指定先が無い場合は `ConfigError` で止め、移設し損ねた鍵を拾って動かない。
3. **状態を機械検査に変換する。** `scripts/check-secret-outside-workspace.sh` が、環境ファイルがワークスペース内に在ることをpre-commitで検出する。`.gitignore` と `check-no-private-data.sh` はコミットへの混入を止めるが、混入しなくてもファイルが在るだけで読める。止めたい状態が違うため検査を分ける。

## 結果

鍵がコンテナ内に存在しなくなり、セッションの子プロセス・hooks・MCPサーバーのいずれからも読めなくなる。ADR-0002・ADR-0003の線引き（外部へ送るのは構造化抽出の投稿本文だけ）が、鍵についても経路として成立する。

受け入れた不利益と残る作業:

- **セッション内から実収集ができなくなる。** キーを要する収集元（YouTube / Reddit / トークン付きGitHub）は、鍵の無いコンテナ内では `ConfigError` で止まる。定期収集はホスト側cronの担当であり（ADR-0007）、開発時の検証は認証不要のBluesky検索で行う（sns-collector/CLAUDE.md「質の確認に本収集を使わない」）。
- **`SNS_COLLECTOR_ENV_FILE` が指す先が無いと、トークンが任意のGitHub収集も止まる。** 以前は鍵が無ければ匿名で走っていた。明示的な指定が外れている状態を、レート制限の下がった劣化状態として黙って続けるより、止めて気づかせるほうを採る。
- **移設そのものは手作業で、機械化していない。** ホスト側のファイル移動はコンテナ内から実行できない。検査は「移せていないこと」を検出するだけである。
- **経路3は塞がっていない。** 閉じたのは「鍵が読まれる」という一事例であり、ワークスペース内の他のファイル（収集済みのJSONL・DB）は従来どおり子プロセスから読める。これらは元よりセッションが読む前提の資産であり、境界の外へは出ない（ファイアウォール）。
- 鍵は既にセッションから読める状態に置かれていた期間がある。**移設と合わせて失効・再発行し、最小権限のスコープで発行し直す。**
- ワークスペース外へ出したことで、鍵は `.gitignore` と `check-no-private-data.sh` の射程からも外れる。移設先を別のリポジトリ配下へ置かない。
- ADR-0008の判断4は「cwdを移すとpython-dotenvがsns-collector本体の `.env` を誤って拾う」ことを `--directory` の根拠に挙げていた。**この根拠は失効する**（暗黙の探索自体をやめたため）。`--directory` を残す理由は、相対パスの解決先をトピック側へ揃えることだけになる。
