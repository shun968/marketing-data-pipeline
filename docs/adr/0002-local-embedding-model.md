# ADR-0002: 埋め込み生成はローカルモデルで行う

- ステータス: 採用
- 日付: 2026-07-28
- 関連: [requirements.md](../requirements.md) N-02 / [design.md](../design.md) §4.4

## コンテキスト

意味検索（F-10）とクラスタリング（F-11）にはベクトル埋め込みが必要である。クラウドの埋め込みAPI（OpenAI、Vertex AI、Cohere等）は品質と手軽さで優れるが、投稿テキストを外部へ送信することになる。

一方、構造化抽出（ADR-0003）ではClaude Code経由で投稿本文をAnthropicへ送信する方針を採っている。「抽出では送るのに埋め込みでは送らない」のは一見不整合に見えるため、判断の根拠を明記する必要がある。

### 検討した選択肢

| 案 | 却下理由 |
|---|---|
| クラウド埋め込みAPI | 検索のたびに外部送信・従量課金。モデル変更時の全件再生成コストが大きい |
| 埋め込みを使わず全文検索のみ | 表記揺れ（「面倒」「めんどい」「だるい」）を吸収できず、F-10を満たせない |
| Claude Code経由で埋め込み生成 | 埋め込みは数値ベクトルの生成であり、対話セッション経由での取得は非現実的 |

## 決定

**埋め込み生成はローカルモデルで行い、外部APIを使用しない。**

判断の根拠:

1. **抽出と埋め込みは頻度が2桁違う。** 抽出は1投稿につき1回だけ（結果を凍結するため）。埋め込みは検索クエリのたびに発生し、モデル変更時には全件再生成が必要になる。外部APIに依存すると、検索という日常操作のたびに外部送信と従量課金が発生する。
2. **追加課金を発生させない（N-04）。** ローカルモデルなら再生成コストがゼロで、モデルの入れ替え・比較を気軽に試せる。
3. **オフラインで完結し、cronで無人実行できる。** APIキー管理・レート制限・障害対応が不要になる。
4. **埋め込み対象は要約文であり短い。** 抽出済み `summary`（1文）を埋め込むため、長文をローカルで処理する必要がない。ローカルモデルでも十分な速度が出る。
5. **埋め込み品質の要求水準が抽出ほど高くない。** 検索は「候補を絞る」ためのものであり、最終判断は人間が投稿本文を読んで行う。多少の精度差は運用で吸収できる。

## 結果

- 検索・クラスタリングが外部送信を伴わない。モデルの入れ替えと全件再生成を課金なしで試せる
- 埋め込み品質はクラウドAPIに劣る可能性がある。検索を「候補の絞り込み」に留め、最終判断を人間が行う運用でこれを吸収する
- 推論速度が実行環境のCPU/GPUに依存する。長文ではなく要約文（1文）を対象とすることで負荷を抑える
- **具体的なモデルは未選定（未確定事項 O-02）。** Phase 3 で実データを用いて選定し、結果を本ADRへ追記する。選定基準は次の4点。
  - 日本語の意味的類似性の精度
  - 実行環境のCPU/GPUで許容できる推論速度
  - ベクトル次元（ストレージと検索速度に影響）
  - ライセンス

### モデル選定の結果（2026-08-08、Phase 3）

**`intfloat/multilingual-e5-large`（次元1024、MITライセンス）を採用する。**

埋め込み生成ライブラリは `fastembed`（ONNX Runtime、torch非依存）を採用した。`sentence-transformers`はtorch込みで1GB超の依存になり、cronでの無人実行・依存の軽さを優先して見送った。

`fastembed` の候補モデル一覧（`TextEmbedding.list_supported_models()`）から、日本語を含む多言語対応かつ商用利用を妨げないライセンスのものを3件に絞り、ローカルDBの実データ（`insights.summary` 264件、抽出プロンプトの仕様によりプラットフォーム・原文言語を問わず日本語で統一されている）で比較した。

| モデル | 次元 | ライセンス | 埋め込み速度(264件) | 意味的な精度 |
|---|---|---|---|---|
| sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2 | 384 | apache-2.0 | 49.7件/秒 | 上位が緩く、無関係な投稿が紛れ込む |
| sentence-transformers/paraphrase-multilingual-mpnet-base-v2 | 768 | apache-2.0 | 16.9件/秒 | MiniLMより明確に改善 |
| **intfloat/multilingual-e5-large** | **1024** | **mit** | 5.4件/秒 | 関連投稿の上位集中が最も明確（類似度0.86〜0.89 vs 他候補は0.55〜0.80） |

「Jetsonのメモリ不足で困っている」「アノテーション作業がつらい」「ローカルLLMの推論が遅い」という3クエリで上位5件を目視比較した結果、`multilingual-e5-large` だけが上位5件を関連投稿でほぼ独占した（他候補は3Dプリント関連など無関係な投稿が上位に紛れた）。速度は他候補の1/3〜1/9だが、`embed` はcronでの差分処理（未埋め込み分のみ）であり、`search` はクエリ1件の埋め込みのみが対象のため、この速度差は実運用上ほぼ影響しない。**意味検索の精度を最優先する（判断根拠1参照）** という当初の基準に従い、最も精度の高いモデルを選ぶ。

**利用上の注意**: `multilingual-e5-*` 系は非対称プレフィックス（ドキュメント側 `passage: `、クエリ側 `query: `）を前提に学習されている。`embed`/`search` の実装ではこのプレフィックスを必ず付与する。付けずに使うと精度が明確に落ちる。

**検索の応答時間について**: HNSW等の近似最近傍インデックスは導入しない。DuckDB VSS拡張は `INSTALL vss; LOAD vss;` でロード自体は確認できたが、HNSWインデックスは固定長 `FLOAT[N]`（ARRAY型）のみ対応しており、可変長の `FLOAT[]`（LIST型、`insights.embedding` の型）には張れない。合成データ（次元1024、100,000行）で `list_cosine_similarity` による総当たり検索を実測したところ0.36秒であり、design.md §5.3の「年間10万件規模ではテーブルスキャンで足りる」という既存方針の範囲に収まる。そのため総当たりのままとし、インデックス化は将来コーパスが増えて実測上遅くなってから検討する。
