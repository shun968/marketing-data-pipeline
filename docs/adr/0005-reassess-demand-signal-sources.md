# ADR-0005: Bluesky単独では需要シグナルの流入が足りないと判断し、収集元の追加を次の検証項目にする

- ステータス: 採用
- 日付: 2026-08-08
- 関連: [requirements.md](../requirements.md) §3 / [roadmap.md](../roadmap.md) Phase 0, Phase 2 / [ADR-0003](./0003-batch-extraction-via-claude-code.md)

## コンテキスト

Phase 0〜2を通し、10日間の収集（1,356件）と100件の構造化抽出を終えた。ここで初めて、当初の前提を実測と突き合わせられる状態になった。

**在庫は回収できたが、フローが立ち上がらない。**

issue #12 で、日本語キーワードが初回収集で在庫を回収しきり、以降の新規がほぼゼロになることを観測した。英語キーワードを追加して在庫は倍増したが、フローは変わらなかった。

| 日付 | Blueskyの収集数 |
|---|---|
| 2026-08-02 | 840件（英語キーワード追加による一括回収） |
| 2026-08-03〜08-07 | 3 / 1 / 2 / 3 / 4 件 |

定常状態は **約2.6件/日**である。抽出の歩留まりは100件中21件が洞察（21%）、支払い意思が読めたものは2件（2%）だった。掛け合わせると次になる。

| 指標 | 到達速度 |
|---|---|
| 洞察 | 0.6件/日（月19件） |
| 支払い意思のある声 | 17日に1件 |

同期間のYouTubeは15.6件/日で安定しており、供給シグナル側は機能している。問題は需要シグナルの収集元に限られる。

### ドメイン別の比較は、まだ結論を出せる状態にない

当初、抽出された洞察の生数（`edge_ai` 13件 / `fabrication` 7件 / `ai_accuracy` 1件）から序列を読もうとした。**これは誤りだった。** ドメインごとに抽出のカバー率が大きく違う。

| ドメイン | 収集 | 抽出済 | カバー率 | 洞察 | 抽出あたりの密度 |
|---|---|---|---|---|---|
| `ai_accuracy` | 79 | 9 | 11% | 1 | 11% |
| `edge_ai` | 264 | 39 | 15% | 11 | 28% |
| `fabrication` | 423 | 28 | 7% | 7 | 25% |

`edge_ai` の生数が多いのは、`fabrication` の2倍のカバー率で抽出したからである。母集団は `fabrication` が最大で、密度は両者ほぼ同じ。`ai_accuracy` の密度は低いが、**n=9では判断材料にならない**。

抽出の対象は「収集日の新しい順」で選んでおり、ドメインで層化していない。この偏りは設計上の帰結であって、データが語っている内容ではない。

### 検討した選択肢

| 案 | 却下理由 |
|---|---|
| 現状のまま収集を続け、時間で件数を稼ぐ | 支払い意思のある声が17日に1件では、仮説の棄却も採択も判断できない。Phase 3以降を積んでも上限がここで決まる |
| キーワードをさらに増やす | 在庫の回収は増えるがフローは増えない。日本語→英語で実証済みであり、同じ操作を繰り返すことになる |
| Blueskyの収集頻度を上げる | 流入がプラットフォーム上の投稿量で決まっており、取得頻度の問題ではない |
| ドメインの優先順位を今ここで組み替える | 抽出カバー率が7〜15%と低く、しかもドメイン間で偏っている。いま順位を決めると、サンプリングの偏りを事業判断として固定してしまう |

## 決定

**Blueskyを需要シグナルの唯一の収集元とする前提を破棄し、収集元の追加を次の検証項目とする。ドメインの優先順位は、層化した抽出で偏りを解消するまで変更しない。**

判断の根拠:

1. **流入速度が事業判断の要求と2桁ずれている。** 月19件の洞察では、ドメイン別・痛み強度別に分けた時点で各セルが1桁になり、傾向を読めない。基盤の完成度ではなく入力の量が律速している。
2. **在庫とフローは別の問題である。** 日本語で在庫を回収しきり、英語で在庫を足し、また回収しきった。キーワード設計で解けるのは在庫だけであり、フローはプラットフォームの選択で決まる。この因果は2回の独立した観測で確認している。
3. **流入不足の判断は抽出のカバー率に依存しない。** 日次の収集件数だけで決まるため、上記のサンプリング偏りの影響を受けない。ドメインの序列とは独立に確定できる。
4. **順位の変更を保留するのは、根拠が偏っていると分かったためである。** 生数の比較は「多く抽出したドメインが多く見つかる」以上のことを語っていなかった。

## 結果

### 収集元の追加が次の作業になる

issue #12 がフォールバックとして挙げていた候補（Reddit の r/3Dprinting・r/LocalLLaMA、Mastodon系、はてなブックマーク）が、いまや本命の選択肢である。**どれを採るかはこのADRでは決めない。** APIの制約・利用規約・認証要否の調査が要り、選定自体が別の判断になる。

Redditを採る場合、既存の設計との整合で確認すべき点が2つある。

- 認証が要る（Blueskyは認証不要だった）。`.env` に資格情報が増え、鍵の管理範囲が広がる
- サブレディット単位の購読はキーワード検索と収集モデルが異なる。`posts.matched_keywords` に何を入れるかの再定義が要る

### 抽出の選択にドメインの層化が要る

現在の `extract prepare` は収集日の新しい順に取るだけで、ドメインを見ていない。ドメイン間の比較を成立させるには、各ドメインから同程度に抽出する仕組みが要る。

**これは新しい要求である。** design.md §4.3 が規定する選択順（収集日の新しい順）はドメインでの層化を意図しておらず、Phase 2 の完了条件も総件数しか見ていなかった。「100件抽出した」ことと「ドメインを比較できる」ことは別だと、実測して初めて分かった。

### 基盤側の作業は止めない

Phase 3以降（埋め込み・グラフ・レポート）は収集元と独立しているため、予定どおり進めてよい。ただし**現在のデータ量では意味検索の精度もクラスタリングの妥当性も評価できない**点は認識しておく。100件規模でHNSWの挙動を測っても、10万件想定の判断材料にはならない。

### 受け入れる不利益

- **10日間の収集で得た結論が「収集元を変える」であり、Bluesky向けに作ったキーワード36件の大半が使い回せない可能性がある。** プラットフォームごとに検証が要ることは既に実測している（同じ語がBlueskyとYouTubeで根本的に違う結果になった）
- **収集元が増えると正規化アダプタと重複排除の対象が増える。** `posts` のスキーマはプラットフォーム差異を吸収する設計になっているが、実際に3つ目を通すまで十分性は分からない
- **ドメインの優先順位が宙に浮いたままPhase 3へ進む。** `fabrication` が主軸に足るという感触（issue #12 の痛み表現率44%、支払い意思2件のうち1件、母集団423件が最大）はあるが、根拠として提示できる状態ではない

### 未解決のまま残る事項

- 追加する収集元の選定（上記）
- `ai_accuracy` の扱い。抽出済み9件のうち洞察1件だが、この標本数では否定も肯定もできない。`inference_placement` と同じ「想定顧客が公開SNSで発話しない」型である可能性は残る。層化抽出で母集団79件を消化してから判断する
- `edge_ai` の内容の偏り。洞察11件の大半が「ローカルLLMが遅い」に集中しており、事業機会として分散していない。追加収集で多様性が出るかは現時点で判断できない
