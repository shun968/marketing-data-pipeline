## 1. 要望（何を実現したいか）

個人開発でサービスを立ち上げるにあたり、**思いつきではなく観測されたシグナルから事業仮説を立てたい**。

SNS上には、まだ製品化されていない不満・欲求が言語化されて存在する。それを継続的に収集・構造化・検索できる基盤をローカルに持つことで、以下を可能にする。

- **潜在的な顧客要望の発見**: 「〜が面倒」「〜が欲しい」といった未充足ニーズの観測
- **製品優位性の探索**: 既存ソリューションへの不満から、差別化の切り口を得る
- **仮説の裏付け**: 思いついた事業アイデアについて、実際に需要シグナルが存在するかを検索で確認する
- **時系列での変化把握**: あるニーズが増えているのか、一過性なのか

### この基盤が満たさなくてよいこと

- リアルタイム性（日次〜週次の粒度で十分）
- 網羅性（母集団の代表性は求めない。仮説の種が得られればよい）
- 他者との共有（個人利用のみ）
- SNSアカウントの個人特定・追跡（分析対象はあくまで「言及内容」）

## 2. 現状と課題

`sns-collector`（#2）でBluesky/YouTubeのキーワード検索データを日次収集し、`data/{platform}/<日付>.jsonl` に追記している。

| 課題 | 内容 |
|---|---|
| **C1. 横断検索できない** | JSONLへの追記のみで、日付・プラットフォームを跨いだ検索ができない |
| **C2. 意味検索できない** | 表記揺れ（「面倒」「めんどい」「だるい」）を吸収した検索ができない |
| **C3. 意味が構造化されていない** | 投稿本文は自然言語のまま。「これはニーズか、不満か、単なる感想か」が機械的に判別できない |
| **C4. 関係性が見えない** | 誰がどの製品に言及したか、どのキーワードが共起するかが追えない |
| **C5. 重複排除が分散している** | `state/{platform}_seen.json`（SeenStore）が独立した状態を持ち、DBと二重管理になる |
| **C6. 収集キーワードが目的とズレている** | 現在の `新規事業` `スタートアップ アイデア` では「新規事業について語る人」しか取れず、市場の生の不満が取れていない |

**C6が最も重大である。** 分析基盤をどれだけ作り込んでも、入力が目的に合っていなければ出力は得られない。本ドキュメントではC6を先に扱う。

## 3. キーワード戦略の再定義

### 3.1 プラットフォームごとの役割分担

BlueskyとYouTubeは検索対象が根本的に異なるため、同じキーワードを使うのは誤りである。

| | Bluesky | YouTube |
|---|---|---|
| 検索対象 | 投稿本文（生の発話） | 動画のタイトル・説明文 |
| 得られるもの | **需要シグナル** — 不満・欲求の一次表現 | **供給シグナル** — 既存ソリューション、競合、市場の関心度 |
| キーワード設計 | 痛みシグナル語 × ドメイン語 | ドメイン語 × 製品カテゴリ語 |

動画タイトルに「〜が面倒」と書く人はほぼいない。YouTubeに痛みシグナル語を投げても空振りする。**YouTubeは「その領域に既にどんな解決策が存在し、どれだけ関心を集めているか」を測る用途に限定する。**

### 3.2 Bluesky: 痛みシグナル語 × ドメイン語

**痛みシグナル語**（ドメイン非依存・未充足ニーズが表出する定型表現）

| 分類 | 語例 |
|---|---|
| 手間・煩雑 | `面倒` `めんどい` `だるい` `手作業` `いちいち` `毎回やってる` |
| 欠落 | `〜がない` `誰か作って` `あったらいいのに` `探してるけどない` |
| 不満・離脱 | `使いにくい` `重い` `高い` `解約` `乗り換え` `代替` |
| 支払い意思 | `課金してでも` `有料でもいい` `金払うから` |
| 自作回避 | `自作した` `スプレッドシートで管理` `スクリプト書いた` |

**支払い意思**と**自作回避**は特に価値が高い。前者は課金可能性の直接的な表明、後者は「既存製品では解決されず、自力で解決するほど強い痛み」を示す。

**ドメイン語**は、個人開発で参入可能な領域に絞って別途定義する（`config/keywords.yaml` 参照）。ドメインを絞らずに痛みシグナル語だけで収集するとノイズが支配的になるため、必ず組み合わせる。

### 3.3 キーワード設計の運用ルール

- キーワードは固定ではなく**仮説検証のパラメータ**として扱う。収集結果を見て継続的に改訂する
- 改訂履歴を `config/keywords.yaml` のコメントに残す（いつ・なぜ追加/削除したか）
- YouTube Data APIのクォータ制約（`search.list` = 100ユニット/回、1日10,000ユニット）を守る。`1日の実行可能回数 ≈ 10000 / (100 × キーワード件数)`

## 4. 機能要件

### 4.1 永続化（C1, C5に対応）

| ID | 要件 |
|---|---|
| F-01 | JSONLファイルからDBへ投稿データをロードできる。同一ファイルの再実行で重複が発生しない（冪等） |
| F-02 | Bluesky/YouTubeを共通スキーマに正規化しつつ、プラットフォーム固有情報は原文JSONとして保持する |
| F-03 | 重複排除は投稿IDによりDB内で完結する。`state/*_seen.json`（SeenStore）は廃止し、DBに統合する |
| F-04 | 収集済みJSONLが残っている限り、DBの投稿データは再構築可能である |

### 4.2 構造化抽出（C3に対応）

| ID | 要件 |
|---|---|
| F-05 | 投稿本文から以下を抽出し、構造化フィールドとして永続化できる: 洞察種別 / ドメイン / 要約 / 痛みの強さ / 収益化可能性 / 競合言及 / 確信度 |
| F-06 | 抽出は投稿ごとに一度だけ行い、結果を確定値として凍結する。検索時に再解釈しない |
| F-07 | 未抽出の投稿を抽出待ちバッチとして書き出し、抽出結果を検証してDBへ投入できる |
| F-08 | 抽出ロジックのバージョンを記録し、将来ロジックを変更した際に再抽出対象を特定できる |

**F-06の根拠**: 検索のたびにLLMへ投げるのは、コスト・再現性・監査可能性のすべてで劣る。一度だけ推論し、以降は「確定した事実」として扱う。

### 4.3 検索（C1, C2に対応）

| ID | 要件 |
|---|---|
| F-09 | SQLによる絞り込み検索ができる（期間・プラットフォーム・ドメイン・洞察種別・痛みの強さ） |
| F-10 | 自然言語クエリによる意味検索ができる（「決済まわりの不満」で表記揺れを跨いで検索） |
| F-11 | 類似する洞察をクラスタとして把握できる |

### 4.4 関係性分析（C4に対応）

| ID | 要件 |
|---|---|
| F-12 | アカウント・キーワード・製品・ドメイン間の関係をエッジとして記録・探索できる |
| F-13 | キーワードの共起関係を集計できる |

### 4.5 レポート（要望に対応）

| ID | 要件 |
|---|---|
| F-14 | 指定期間の定量サマリをMarkdownで自動生成できる（新規観測件数、ドメイン別分布、痛み強度分布、頻出キーワード、代表投稿） |
| F-15 | F-14の生成は完全自動であり、cronで定期実行できる |
| F-16 | 定量サマリを入力として、洞察・仮説を加筆したレポートを作成できる |

## 5. 非機能要件

| ID | 分類 | 要件 |
|---|---|---|
| N-01 | データ管理 | 収集データ・DB・レポートはローカルディスクにのみ保存し、リポジトリにコミットしない |
| N-02 | 外部送信 | 埋め込み生成はローカルモデルで行い、外部APIへ投稿本文を送信しない |
| N-03 | 外部送信 | 構造化抽出はClaude Codeセッションを経由する。**投稿本文がAnthropicへ送信される**（後述の方針変更を参照） |
| N-04 | コスト | パイプライン本体はLLM APIを呼ばない。追加の従量課金が発生しない構成とする |
| N-05 | 再現性 | 抽出結果はバッチファイルとして残し、いつ・どのバージョンで抽出したかを追跡できる |
| N-06 | 規模 | 数百件/日、年間10万件規模を想定。この規模で検索が実用的な応答時間に収まること |
| N-07 | 可搬性 | DBは単一ファイルとし、ディレクトリのコピーでバックアップ・移設が完結すること |
| N-08 | 依存 | 常駐プロセス（DBサーバ等）を必要としないこと |
| N-09 | 開発環境 | Python 3.11以上、uv、既存の `sns-collector` パッケージ構成を踏襲する |

### 方針変更: 外部送信ポリシー（N-03）

issue #2/#3では「収集データは外部へ送信・公開しない」を前提としていた。本要件定義では、構造化抽出の実現手段としてClaude Codeを用いるため、**投稿本文がAnthropicへ送信される**点でこの前提を一部変更する。

| 対象 | 変更前 | 変更後 |
|---|---|---|
| 収集した生データ（JSONL） | ローカルのみ | ローカルのみ（変更なし） |
| DB本体 | — | ローカルのみ |
| 埋め込み生成 | — | ローカルのみ（外部送信なし） |
| リポジトリへのコミット | しない | しない（変更なし） |
| **構造化抽出時の投稿本文** | 送信しない | **Claude Codeセッションへ送信する** |

対象データはいずれも公開SNS上の公開投稿であり、非公開情報を含まない。この変更はissue #3のコメントとして記録する。

## 6. スコープ外

- 収集対象プラットフォームの追加（X/Twitter、Reddit等）
- YouTubeコメントの取得
- クラウド環境での実行・ホスティング
- Webダッシュボード等のGUI
- 複数人での共有・権限管理
- AI PRレビューやlint規律の整備（開発自走基盤側の課題として別issueで扱う）
