## 進め方

各Phaseは1PRを原則とし、完了条件を満たしてからマージする。Phase 0のみ他Phaseと並行して先行させる。

**Phase 0を最優先で着手する。** 現時点で収集データが1件も存在せず、実データなしでスキーマを確定させると作り直しになるため。Phase 0で収集を回し始めておけば、Phase 1に着手する頃には検証用のサンプルが溜まっている。

---

## Phase 0: キーワード戦略の再定義と収集開始

**目的**: 目的に合ったデータを溜め始める。他Phaseの前提となる実サンプルを確保する。

| # | 作業 |
|---|---|
| 0-1 | 対象ドメインを3〜5個選定し `config/domains.yaml` を作成する（未確定事項 O-01） |
| 0-2 | `config/keywords.yaml` を痛みシグナル語×ドメイン語の構成へ改訂する |
| 0-3 | YouTubeのキーワードをドメイン語×製品カテゴリ語へ分離する |
| 0-4 | YouTube Data APIのクォータ計算に基づきcron頻度を調整する |
| 0-5 | cronを登録し、収集を開始する |
| 0-6 | 2〜3日後にヒット件数と内容の質を確認し、キーワードを1回改訂する |

**完了条件**
- 両プラットフォームで日次収集が動作している
- Blueskyで痛みシグナルを含む投稿が実際に取得できている
- 手動レビューで「これは事業仮説の種になる」と判断できる投稿が複数含まれている

**リスク**: キーワードが空振りする場合、Phase 1以降に進んでも意味がない。0-6の確認で質が不十分なら、改訂を繰り返してから先へ進む。

## Phase 1: DB基盤とロード

**目的**: JSONLをクエリ可能にする。SeenStoreを統合する。

対応要件: F-01〜F-04, N-06〜N-09

| # | 作業 |
|---|---|
| 1-1 | `db/` モジュールを新設し、DuckDB接続とスキーマ管理を実装する |
| 1-2 | `posts` `insights` `edges` `extraction_batches` `schema_version` のDDLを作成する |
| 1-3 | Bluesky/YouTubeの正規化アダプタを実装する |
| 1-4 | `db init` / `db load` コマンドを実装する |
| 1-5 | `SeenStore` を廃止し、重複判定をDBの主キー制約へ移行する（ADR-0004） |
| 1-6 | 既存の `state/*_seen.json` からの移行手順をREADMEに記載する |
| 1-7 | 正規化・冪等性の単体テストを追加する |

**完了条件**
- Phase 0で収集したJSONLが全件DBへ投入できる
- 同一ファイルを2回ロードして件数が変わらない（テストで担保）
- 収集コマンドがSeenStoreを参照せず動作する
- `SELECT` で期間・プラットフォーム横断の検索ができる

## Phase 2: 構造化抽出

**目的**: 投稿を検索・集計可能な洞察へ変換する。本基盤の中核。

対応要件: F-05〜F-08, N-03〜N-05

| # | 作業 |
|---|---|
| 2-1 | 抽出スキーマを確定し、Pydanticまたはdataclassで検証ロジックを実装する |
| 2-2 | 抽出プロンプト `v1` を作成する（`insight_type` `pain_level` の判定基準を明文化） |
| 2-3 | `extract prepare` を実装する（バッチJSONL＋作業指示Markdownの生成） |
| 2-4 | `extract load` を実装する（スキーマ検証・post_id照合・エラー隔離） |
| 2-5 | `extract status` を実装する |
| 2-6 | 20件程度の小バッチで試行し、抽出品質を人手で評価する |
| 2-7 | 評価結果をもとにプロンプトを改訂し、`v2` として再試行する |
| 2-8 | 1バッチあたりの適正件数を実測で決定する（未確定事項 O-03） |
| 2-9 | 検証ロジックの単体テストを追加する（正常系・スキーマ違反・不正post_id・重複） |

**完了条件**
- 100件以上の投稿に対して抽出結果がDBへ投入されている
- 抽出結果を人手でレビューし、実用に足る品質だと判断できる
- 不正な結果ファイルが確実に拒否され、DBが汚染されないことをテストで担保している
- 1バッチの所要時間が15分以内に収まっている

**注意**: 2-6で品質が不十分な場合、Phase 3へ進まずプロンプト改善を優先する。抽出品質は下流すべての品質上限になる。

## Phase 3: 埋め込みと意味検索

**目的**: 表記揺れを跨いだ検索を可能にする。

対応要件: F-10, F-11, N-02

| # | 作業 |
|---|---|
| 3-1 | ローカル埋め込みモデルを複数候補で比較し選定する（未確定事項 O-02） |
| 3-2 | `embed` コマンドを実装する |
| 3-3 | DuckDB VSS拡張を導入し、HNSWインデックスの永続化挙動を検証する |
| 3-4 | `search` コマンドを実装する（意味検索＋構造化絞り込み＋全文検索の合成） |
| 3-5 | 実データで検索精度を評価する |

**完了条件**
- 全 `insights` に埋め込みが付与されている
- 「決済まわりの不満」のような自然言語クエリで、表記揺れを跨いだ結果が返る
- 外部APIを一切呼ばずに埋め込み生成が完結している
- 検索が実用的な応答時間に収まっている
