# 抽出指示 v1(maritime-collector)

投稿から事業仮説の材料になる洞察を1件ずつ抽出する。

スキーマ・判定基準は sns-collector/prompts/extract-v2.md のトピック非依存部分を引き継いでいる
（ADR-0008。同じ抽出パイプラインを別トピックへ向けて再利用しているため）。
ドメイン固有の判定は「domain」節と「competitors」の例のみ、この基盤（船舶/AR/衝突予知・衝突予防）向けに書き換えてある。

## 手順

1. `{batch_jsonl}` を読む。1行1投稿のJSONL
2. 各投稿について下のスキーマに従って判定する
3. `{result_jsonl}` へ1行1結果のJSONLで書き出す。**入力と同じ件数・同じ順序**

## 出力スキーマ

```json
{
  "post_id": "入力の id をそのまま。作らない・変えない",
  "insight_type": "need | complaint | advantage | workaround | none",
  "domain": "{domain_ids}",
  "summary": "この投稿が示すニーズを1文で。日本語。400字以内",
  "pain_level": 0,
  "monetizable": false,
  "competitors": ["言及された既存製品・サービス名"],
  "confidence": 0.0
}
```

## insight_type の判定

| 値 | 意味 | 例 |
|---|---|---|
| `need` | 未充足のニーズ。「こういうものが欲しい/あれば」 | 「見張りを支援してくれる装置が欲しい」 |
| `complaint` | 既存の解決策への不満 | 「このARPAはアラートが多すぎて役に立たない」 |
| `advantage` | 差別化の示唆。既存にない強みへの言及 | 「この装置だけは夜間でも誤報が少ない」 |
| `workaround` | 自作回避。既存で満たせず自分で作った | 「無いので自分でAISの表示を見やすく改造した」 |
| `none` | 上記のいずれでもない | 製品発表、ニュース、記事の要約、単なる感想、bot投稿 |

**迷ったら `none` にする。** 誤って洞察として拾うと、下流の集計が薄まる。取りこぼしは次のキーワード改訂で回収できるが、誤検出はDBに残り続ける。

`none` のとき `domain` と `summary` は不要、`pain_level` は必ず 0。

### 「誰の困りごとか」で判断する

**投稿者本人の体験である必要はない。** 判定の基準は、**具体的な人物の具体的な困りごとが書かれているか**である。

| 投稿の形 | 判定 |
|---|---|
| 本人が困っている | 該当する種別で拾う |
| **他者の困りごとを引用している**（ブログ・記事の一節など） | **拾う。** ただし `confidence` を 0.6 未満にする |
| 記事の要約・紹介。困りごとが書かれていない | `none` |
| 製品発表・リリース情報 | `none` |
| 既存製品の推薦・構成の共有（「私はこれを使っている」） | `none`。ただし `competitors` には記録する |
| 本人の手順ミスによる失敗（操作忘れ・確認漏れ等） | `none`。装置やツールの不足ではない |

引用でも拾う理由: 「既存のARPAでは狭視界時のアラートが信用できず、結局肉眼の見張りに頼っている」のような一節は、それ自体が需要シグナルそのものである。誰が言ったかではなく、市場に何が不足しているかを見る。

### 同じ内容の投稿が複数あるとき

**それぞれ独立に判定する。重複を `none` にしない。** 同じ記事が複数アカウントから共有されることがあるが、投稿は別々の事実であり、除去は集計側の仕事である。

## pain_level の判定

| 値 | 意味 |
|---|---|
| 0 | 言及のみ。困っているとは読めない |
| 1 | 軽い不便。「ちょっと面倒」程度 |
| 2 | 明確な障害。作業が止まる・回避策を探している |
| 3 | 強い痛み。支払い意思・時間の大量消費・断念が読み取れる |

## monetizable

**投稿から支払い意思が読み取れるときだけ `true`。** 「有料でもいい」「金を払うから」「時間を買いたい」等。
「便利そう」「あったらいいな」は `false`。ここを緩めると事業判断の材料にならない。

**コストの比較は支払い意思ではない。** 「自前の見張り要員より装置のほうが安い」は、むしろ既存手段で足りている証拠なので `false`。

## competitors

言及された既存製品・サービス名。**`insight_type` が `none` でも記録する。** 供給側の分析に使うため、洞察の有無とは独立している。

一般名詞は入れない（「レーダー」ではなく「Furuno FAR-2xx8」のような具体的な機器・製品名）。

## confidence

判定そのものへの確信度。低いものは検索から除外できるようにするための値。

- 0.9以上: 投稿が明示的に述べている
- 0.6〜0.9: 文脈から読み取れる
- 0.6未満: 推測が入る。**他者の引用から拾ったものはここ**

## 判断に迷う場合

- **投稿が短く文脈が足りない** → `none` / `confidence` を下げる
- **複数の洞察を含む** → 最も強いもの1つを選ぶ。1投稿1行を守る
- **英語の投稿** → `summary` は日本語で書く。集計を1言語に揃える
- **どのドメインにも当てはまらない** → `other`

## 守ること

- **入力に無い `post_id` を書かない。** 検証で拒否され、その投稿は再バッチになる
- **1投稿につき1行。** 重複は拒否される
- **投稿本文をそのまま `summary` に写さない。** 「この投稿が示すニーズ」へ圧縮する。この1文が後段の意味検索の入力になるため、ノイズ（絵文字・URL・定型句）を持ち込まない
