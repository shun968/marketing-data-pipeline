# CLAUDE.md — sns-collector

SNS投稿の収集ツール（Python 3.11+ / uv）。

リポジトリ全体の規約はルートの `CLAUDE.md` にある。ここには**この領域に固有の規約だけ**を置く。

## 開発コマンド

```sh
uv sync                     # 依存インストール
uv run pytest               # テスト
uv run ruff check .         # lint
uv run ruff format .        # フォーマット
uv run sns-collector bluesky   # 収集（手動実行）
uv run sns-collector youtube
```

cronで3時間おきに自動収集される（`scripts/cron_run.sh`。flockで多重起動を防いでいる）。

## 収集済みデータを失わない

**バッファに溜めて最後にまとめて書く形を書かない。既存コードにこの形を見つけたら直す。** 新規コードだけの制約ではない。実装前に「処理の途中でプロセスが落ちたら何が失われるか」を必ず確認する。

保存が全キーワード完了後の一括のみだったため、11キーワード目の403で先行201件を破棄した実績がある。現在は3層で防いでいる。

1. **キーワード単位で保存する。** JSONLを先に書き、成功してからDBへ入れる。逆順にすると、書き込み前に落ちた投稿を二度と収集できなくなる（DBに既知として記録済みのため次回スキップされる）
2. **HTTP失敗をキーワード単位で隔離する。** `requests.RequestException` を捕捉してスキップし、次のキーワードへ進む
3. **パース失敗を投稿単位で隔離する。** `from_post` / `from_item` は `post["uri"]` / `item["id"]` を subscript で読むため `KeyError` が起きうる。1件の不正データで同一キーワードの他の投稿まで失わない

この失敗モードは機械的に検出できない。実装時とレビュー時に人が見るしかない。

## コード

Pythonの共通の書き方はルートの `CLAUDE.md` にある。この領域に固有なのは次の1点。

- **ログに投稿本文やAPIキーを出さない**（ログ出力も日本語で書く）

## 分析ストア（DuckDB）

収集は `data/analysis.duckdb` に依存する。重複判定を `posts` の主キーへ一本化したため（ADR-0004）、DBが無ければ既知の投稿を判別できない。

- **接続は `db.connect()` を通す。** 既定でスキーマを最新へ揃えるので、`db init` の実行漏れでcronが落ちない
- **正規化は `db/adapters.py` にだけ置く。** 収集時の投入とJSONLロードは同じアダプタ・同じSQLを通す。ここが分かれると `db load` での再構築が収集時と食い違う
- **スキーマ変更は `MIGRATIONS` の末尾に足す。既存要素を書き換えない。** 適用済みDBには過去のSQLが効いているため、書き換えると新規作成したDBと食い違う
- **JSONLを捨てない。** DBはJSONLから再構築できる状態を保つ（F-04）

## テスト

- **実際のAPI通信を行わない。** `requests` またはその上位関数をモックする
- 新しい失敗モードを修正したら、必ず回帰テストを追加する
- 冪等性は「同じ入力で2回実行して結果が変わらない」ことをテストで担保する

## キーワード設計

`config/keywords.yaml` の改訂時は3原則を必ず守る。**詳細・実測データ・改訂手順は `README.md`** にあるので、変更前にそちらを読む。

1. **固有名詞・技術用語のアンカーを必ず含める。** 日本語には語境界がなく、一般語だけの組み合わせはノイズに埋もれる（`量子化 精度` → 中国語の量子化学）
2. **英字の固有名詞には日本語の語を添える。** 英字のみは英語圏・公式アカウント・botを拾う（`OpenVINO` → GitHubトレンドbot）。**日本語圏を狙うときだけの規則**であり、英語圏向けのキーワードには適用しない
3. **英語では件数でノイズを判定できない。** 上位アカウントの偏りを見る。ブリッジ投稿（`*.brid.gy`）・論文bot・ニュース自動投稿が英語側の主なノイズ源

同名衝突がある語には限定語を添える（`パラレルリンク` → 遊戯王のカード）。変更したら実データをサンプリングして質を確認し、改訂履歴に根拠を残す。

**質の確認に本収集を使わない。** `bluesky/client.py` の `search_posts` は認証不要・副作用なしで呼べる。候補の検証はこれを使い、DBを汚さずに行う（一度 `posts` に入った投稿は二度と収集されない）。
