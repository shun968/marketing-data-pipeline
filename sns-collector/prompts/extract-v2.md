# 抽出指示 v2

投稿から事業仮説の材料になる洞察を1件ずつ抽出する。

v1からの変更点は末尾の「v1からの変更」を見ること。

## 手順

1. `{batch_jsonl}` を読む。1行1投稿のJSONL
2. 各投稿について下のスキーマに従って判定する
3. `{result_jsonl}` へ1行1結果のJSONLで書き出す。**入力と同じ件数・同じ順序**

## 出力スキーマ

```json
{
  "post_id": "入力の id をそのまま。作らない・変えない",
  "insight_type": "need | complaint | advantage | workaround | none",
  "domain": "{domain_ids}",
  "summary": "この投稿が示すニーズを1文で。日本語。400字以内",
  "pain_level": 0,
  "monetizable": false,
  "competitors": ["言及された既存製品・サービス名"],
  "confidence": 0.0
}
```

## domain の判定

`insight_type` が `none` 以外のとき、下のいずれか1つを選ぶ。**この一覧に無い値を書かない。**

{domain_guide}

**隣接するドメインの取り違えに注意する。** 上の各行の後半が、隣との境界である。
どれにも当てはまらないものは `other`（無理にどれかへ寄せない。`other` の比率が
高いこと自体が、統制語彙の不足を示す材料になる）。

## insight_type の判定

| 値 | 意味 | 例 |
|---|---|---|
| `need` | 未充足のニーズ。「こういうものが欲しい/あれば」 | 「〜を自動でやってくれるツールが欲しい」 |
| `complaint` | 既存の解決策への不満 | 「このライブラリは遅くて使い物にならない」 |
| `advantage` | 差別化の示唆。既存にない強みへの言及 | 「Xだけがこの制約下で動く」 |
| `workaround` | 自作回避。既存で満たせず自分で作った | 「無いので自分でスクリプトを書いた」 |
| `none` | 上記のいずれでもない | 製品発表、ニュース、記事の要約、単なる感想、bot投稿 |

**迷ったら `none` にする。** 誤って洞察として拾うと、下流の集計が薄まる。取りこぼしは次のキーワード改訂で回収できるが、誤検出はDBに残り続ける。

`none` のとき `domain` と `summary` は不要、`pain_level` は必ず 0。

### 「誰の困りごとか」で判断する

**投稿者本人の体験である必要はない。** 判定の基準は、**具体的な人物の具体的な困りごとが書かれているか**である。

| 投稿の形 | 判定 |
|---|---|
| 本人が困っている | 該当する種別で拾う |
| **他者の困りごとを引用している**（ブログ・記事の一節など） | **拾う。** ただし `confidence` を 0.6 未満にする |
| 記事の要約・紹介。困りごとが書かれていない | `none` |
| 製品発表・リリース情報 | `none` |
| 既存製品の推薦・構成の共有（「私はこれを使っている」） | `none`。ただし `competitors` には記録する |
| 本人の手順ミスによる失敗（設定忘れ・付け忘れ） | `none`。製品やツールの不足ではない |

引用でも拾う理由: 「スクラッチで設計するのは面倒なので、既存データを探して見つけた」のような一節は、それ自体が需要シグナルそのものである。誰が言ったかではなく、市場に何が不足しているかを見る。

### 同じ内容の投稿が複数あるとき

**それぞれ独立に判定する。重複を `none` にしない。** 同じ記事が複数アカウントから共有されることがあるが、投稿は別々の事実であり、除去は集計側の仕事である。ここで消すと、何件あったかが分からなくなる。

## pain_level の判定

| 値 | 意味 |
|---|---|
| 0 | 言及のみ。困っているとは読めない |
| 1 | 軽い不便。「ちょっと面倒」程度 |
| 2 | 明確な障害。作業が止まる・回避策を探している |
| 3 | 強い痛み。支払い意思・時間の大量消費・断念が読み取れる |

## monetizable

**投稿から支払い意思が読み取れるときだけ `true`。** 「有料でもいい」「金を払うから」「時間を買いたい」等。
「便利そう」「あったらいいな」は `false`。ここを緩めると事業判断の材料にならない。

**コストの比較は支払い意思ではない。** 「自前のハードより従量課金APIのほうが安い」は、むしろ既存手段で足りている証拠なので `false`。

## competitors

言及された既存製品・サービス名。**`insight_type` が `none` でも記録する。** 供給側の分析（どの製品が話題に出るか）に使うため、洞察の有無とは独立している。

一般名詞は入れない（「3Dプリンタ」ではなく「Bambu Lab A1」）。

## confidence

判定そのものへの確信度。低いものは検索から除外できるようにするための値。

- 0.9以上: 投稿が明示的に述べている
- 0.6〜0.9: 文脈から読み取れる
- 0.6未満: 推測が入る。**他者の引用から拾ったものはここ**

## 判断に迷う場合

- **投稿が短く文脈が足りない** → `none` / `confidence` を下げる
- **複数の洞察を含む** → 最も強いもの1つを選ぶ。1投稿1行を守る
- **英語の投稿** → `summary` は日本語で書く。集計を1言語に揃える
- **どのドメインにも当てはまらない** → `other`

## 守ること

- **入力に無い `post_id` を書かない。** 検証で拒否され、その投稿は再バッチになる
- **1投稿につき1行。** 重複は拒否される
- **投稿本文をそのまま `summary` に写さない。** 「この投稿が示すニーズ」へ圧縮する。この1文が後段の意味検索の入力になるため、ノイズ（絵文字・URL・定型句）を持ち込まない

## v1からの変更

v1で20件を抽出した実測に基づく。

1. **引用を拾えるようにした。** v1は「技術ニュースの紹介や引用は none」としていたため、「スクラッチで設計するのは面倒→既存データを探した」という**事業仮説そのものの内容を落としていた**。判定基準を「誰が言ったか」から「具体的な困りごとが書かれているか」へ変えた
2. **重複投稿の扱いを明記した。** v1は指示が無く、判断が揺れる余地があった
3. **`none` でも `competitors` を記録すると明記した。** v1は書いておらず、実際には記録していた（Reolink / Frigate 等）。指示と実態を揃えた
4. **本人の手順ミスによる失敗を `none` と明記した。** v1では判断に迷った（造形失敗だがビルドプレートの付け忘れ）
5. **コスト比較は `monetizable=false` と明記した。** 「自前ハードよりAPIが安い」は既存手段で足りている証拠であり、支払い意思ではない

bot・フィードアカウントの除外は**入れなかった**。ハンドル名のパターンで落とす案を実測したところ、Bluesky未抽出744件のうち87件（11.7%）に当たる一方、その87件にも痛み表現が8%含まれていた。さらに問題の起点だった「今日のAI関連記事」の投稿元（`dailygenaitrends.bsky.social`）はどのパターンにも当たらない。生の声を落としてまで得るものが無いため、`none` として抽出側で処理する。
