# 抽出指示 v1

投稿から事業仮説の材料になる洞察を1件ずつ抽出する。

## 手順

1. `{batch_jsonl}` を読む。1行1投稿のJSONL
2. 各投稿について下のスキーマに従って判定する
3. `{result_jsonl}` へ1行1結果のJSONLで書き出す。**入力と同じ件数・同じ順序**

## 出力スキーマ

```json
{
  "post_id": "入力の id をそのまま。作らない・変えない",
  "insight_type": "need | complaint | advantage | workaround | none",
  "domain": "{domain_ids}",
  "summary": "この投稿が示すニーズを1文で。日本語。400字以内",
  "pain_level": 0,
  "monetizable": false,
  "competitors": ["言及された既存製品・サービス名"],
  "confidence": 0.0
}
```

## insight_type の判定

| 値 | 意味 | 例 |
|---|---|---|
| `need` | 未充足のニーズ。「こういうものが欲しい/あれば」 | 「〜を自動でやってくれるツールが欲しい」 |
| `complaint` | 既存の解決策への不満 | 「このライブラリは遅くて使い物にならない」 |
| `advantage` | 差別化の示唆。既存にない強みへの言及 | 「Xだけがこの制約下で動く」 |
| `workaround` | 自作回避。既存で満たせず自分で作った | 「無いので自分でスクリプトを書いた」 |
| `none` | 上記のいずれでもない | 製品発表、ニュース、単なる感想、bot投稿 |

**迷ったら `none` にする。** 誤って洞察として拾うと、下流の集計が薄まる。取りこぼしは次のキーワード改訂で回収できるが、誤検出はDBに残り続ける。

`none` のとき `domain` と `summary` は不要、`pain_level` は必ず 0。

## pain_level の判定

| 値 | 意味 |
|---|---|
| 0 | 言及のみ。困っているとは読めない |
| 1 | 軽い不便。「ちょっと面倒」程度 |
| 2 | 明確な障害。作業が止まる・回避策を探している |
| 3 | 強い痛み。支払い意思・時間の大量消費・断念が読み取れる |

## monetizable

**投稿から支払い意思が読み取れるときだけ `true`。** 「有料でもいい」「金を払うから」「時間を買いたい」等。
「便利そう」「あったらいいな」は `false`。ここを緩めると事業判断の材料にならない。

## confidence

判定そのものへの確信度。低いものは検索から除外できるようにするための値。

- 0.9以上: 投稿が明示的に述べている
- 0.5〜0.9: 文脈から読み取れる
- 0.5未満: 推測が入る

## 判断に迷う場合

- **投稿が短く文脈が足りない** → `none` / `confidence` を下げる
- **技術ニュースの紹介や引用** → `none`。本人の困りごとではない
- **複数の洞察を含む** → 最も強いもの1つを選ぶ。1投稿1行を守る
- **英語の投稿** → `summary` は日本語で書く。集計を1言語に揃える
- **どのドメインにも当てはまらない** → `other`

## 守ること

- **入力に無い `post_id` を書かない。** 検証で拒否され、その投稿は再バッチになる
- **1投稿につき1行。** 重複は拒否される
- **投稿本文をそのまま `summary` に写さない。** 「この投稿が示すニーズ」へ圧縮する。この1文が後段の意味検索の入力になるため、ノイズ（絵文字・URL・定型句）を持ち込まない
