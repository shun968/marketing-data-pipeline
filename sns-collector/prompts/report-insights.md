# 洞察加筆指示

`sns-collector report` が生成した定量サマリ（`reports/report-<since>_<until>.md`）を入力に、事業仮説の検討に使える洞察・仮説を加筆する（design.md §4.6、F-16）。

**このセッションが行うのは加筆だけ。** 定量サマリの数値そのものを書き換えない。数値が実態と合わないと感じたら、`sns-collector report` 側の集計を疑い、このセッションでは直さない。

## 手順

1. `reports/` 配下で最も新しい `report-<since>_<until>.md` を読む
2. `sns-collector/config/domains.yaml` を読み、各ドメインの `hypothesis`（検証したい仮説）と `service_candidate`（想定するサービス案）を確認する
3. 元のMarkdownの末尾に「## 洞察・仮説」節を追記し、`reports/report-<since>_<until>.md` へ上書き保存する（新規ファイルは作らない。定量部分と洞察部分を1つのレポートとして残す）

## 「## 洞察・仮説」に書くこと

対象は主に次の2セクション。

- **最重要シグナル（pain_level=3 かつ monetizable=true）**: 個々の投稿が `domains.yaml` のどの仮説を支持する／しないかを判定する
- **domain別の件数（前期間比）**: 増減が仮説の検証状況にとって何を意味するかを解釈する

各ドメインについて、次の観点で1〜3行にまとめる。

| 観点 | 書くこと |
|---|---|
| 仮説の検証状況 | このドメインの `hypothesis` を支持する投稿が今期あったか。無ければ「今期は無し」と明記する |
| service_candidate との整合 | 拾えた困りごとは `service_candidate` が解く範囲に収まるか、外れているか |
| 次のアクション | 収集を続ける／キーワードを見直す／仮説を棄却する、のどれに近いか |

「新規に観測された競合製品」がある場合は、`service_candidate` との競合関係（代替か補完か）を一言添える。

## 守ること

- **元の投稿にない主張を作らない。** 加筆は定量サマリに載っている件数・代表投稿URLの範囲に限る。感想や一般論で埋めない
- **仮説を支持する材料が無いドメインは「無い」と書く。** 書かずに省略すると、次にこのレポートを読む人が「確認していない」のか「無かった」のか区別できない
- **加筆は日本語で書く**（CLAUDE.md のPython規約と同じ理由。この基盤の記録は日本語に統一する）
- 定量サマリの表・数値には一切手を触れない
